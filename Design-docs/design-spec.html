Vessel Purchase Order Management System

A complete low-fidelity wireframe and design system for the procurement application used daily by a fleet's purchase, technical, and accounts teams — from raising a purchase request aboard a vessel through RFQ, award, invoicing, and delivery confirmation. Written for direct reconstruction in Figma.

Grounded in
The live Supabase schema already in this repo — real table and status names, not invented ones
Visual direction
Modern enterprise SaaS — Stripe / Linear / Notion-grade, independent of today's UI
Fidelity
Low-fi structural wireframes for pages, live specimens for components & tokens
Scope
19 screens/flows · 14 components · full token set · 3 breakpoints
How to read the wireframes — ( text ) is an input or select, [ Label ] is a button, ▢ is an icon slot (kept as a placeholder mark deliberately — see §6 for the actual icon set), ⋮ is a row-action menu, ··· means "rows repeat." Where a page introduces a status or field that doesn't exist in the current database yet, it's marked NEW; everything else maps to a real column.

04 — Behavior

Interaction notes

Feedback
Every write action confirms itself, in place
Save/submit shows a button loading state (label swaps to spinner, button stays same width), then a toast — never a silent success or a full-page reload.
Confirmation
Only one-way doors get a confirm dialog
Award a vendor, delete a PR, reject an invoice — anything that closes a state or destroys data. Routine saves and status advances do not, to avoid dialog fatigue.
Validation
Inline, on blur — never only on submit
A required-by date in the past, a missing GST number, a quote with no price: flagged the moment the field loses focus, with the fix stated in the helper text, not just "invalid."
Tables
Sticky header, row hover, two tiers of action
Frequent single-row actions (approve, view) sit inline or in a kebab; multi-row actions (bulk issue RFQ, export) only appear once a checkbox is ticked, in a bar pinned above the header.
Navigation
Breadcrumbs on every detail/edit page
A user arriving from search or a notification lands mid-hierarchy — the breadcrumb is their only way back without the sidebar.
Uploads
Progress is visible, failure is row-scoped
Excel import and PDF attachment both show a determinate progress bar; a failed row is fixable in place, not a reason to restart the whole upload.
Motion
Functional only, respects reduced motion
150ms ease-out for drawers/modals entering, 100ms for hover/focus states. No decorative animation; all transitions are disabled under prefers-reduced-motion.

06 — Recommendations

UX recommendations

Specific to this app's actual gaps, not generic best practice — each one points at something found in the repo.

Gap
Most modules currently persist to localStorage as a Supabase stand-in
Until the wiring is complete, show a small per-record "Saved locally" vs. "Synced" indicator so users aren't misled about durability across devices.
Gap
The admin approval queue exists in code with no nav entry
Give it a real home at Settings → Team (wireframed in §4) instead of a buried flow only the original builder knows exists.
Gap
The existing "AI Quote" document-import feature is easy to miss
Surface it as a primary path inside the vendor quote intake step, not a secondary option — it's the single most differentiated feature already in the codebase.
Gap
Every PR/PO/invoice carries a vessel_id, but lists show the whole fleet by default
Default list views to the signed-in user's assigned vessel(s) with an explicit "All vessels" toggle — cuts scan time for anyone not on a fleet-wide desk.
Gap
pr_line_items.status is tracked but never shown in the UI
Surface partial fulfillment ("3 of 5 items awarded") directly on the PR list row instead of only at the whole-PR level.
Gap
PO, invoice, and delivery note are three separate modules today
The PO Detail "thread" view in §4 ties RFQ → quotes → invoice(s) → DN(s) to one PO so nothing needs re-searching by PO number.
Gap
Vendor categories and PR categories are two independent free-text-adjacent lists
Enforce both from the one managed list already started in Settings, so category filters and vendor-matching during RFQ setup stay reliable.
07 — Roadmap

Future enhancements

01
Approval workflows & multi-level permissions
Build on the existing users.role field: amount-based routing (e.g. POs above a threshold require Fleet Manager sign-off after Purchase Officer). Needs new approval_rules and approval_actions tables.
02
Audit log
A single audit_log table (entity, entity_id, actor, action, from_status, to_status, at) backing the Settings → Audit tab wireframed in §4 — every status transition already happens, it just isn't recorded anywhere durable yet.
03
Vendor performance dashboards
Extend the existing vendors.rating field into computed metrics — on-time delivery %, quote responsiveness, price vs. category median — sourced from existing quotes/POs/DNs, surfaced on the Vendor profile (§4) and a fleet-wide leaderboard in Reports.
04
AI-assisted procurement
The codebase already has a seed of this — the "AI Quote" document-import in rfq.js. Extend it to suggest vendors for a new PR from category/vessel history, flag anomalous quote pricing during Compare Quotes, and draft RFQ vendor messages.
05
Mobile receiving companion
Vessel crew confirming deliveries portside often have unreliable connectivity — a lightweight, offline-capable mobile flow for delivery-note confirmation (photo capture, signature) is where mobile investment should go, rather than trying to make full PR entry work on a phone (see §10).
06
Multi-currency reporting rollup
Vendors and POs already carry a currency field; a fleet buying across currencies needs an FX-normalized view in Reports so budget-vs-spend is comparable fleet-wide.
Prepared for direct reconstruction in Figma — component specs in §5 map to Figma components with the listed variant properties; §6 tokens map to Figma styles/variables 1:1. Grounded throughout in the live schema in scripts/supabase-init.js and js/config.js.
